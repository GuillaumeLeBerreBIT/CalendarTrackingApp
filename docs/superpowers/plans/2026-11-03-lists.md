# Quick Lists (Shopping + Event Wishlist) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Fast shopping lists (Enter/paste to add, tap to strike, shared per group) and one claimable wishlist per event whose owner never sees claims.

**Architecture:** One data foundation — `lists` (kind `shopping` | `wishlist`), `list_items`, `list_item_claims` — guarded by RLS built on the existing helpers. A new `routes/lists.js` does everything through `req.supabase` and fills usernames via `supabaseAdmin`. The client gets a "Shopping" tab on the Tasks page and a Wishlist section in `EventModal`, sharing one quick-add input and one pure helper module.

**Tech Stack:** Postgres/Supabase RLS, Express 5 ESM, React 19 + TS, Vitest.

**Spec:** `docs/superpowers/specs/2026-11-03-lists-design.md`

## Global Constraints

- Follow CLAUDE.md: ESM only; every endpoint returns `{ success: true|false, ... }`; `authRequire` on every route; Supabase builders always `await`ed (no `.catch()`).
- Routes read/write **only** through `req.supabase`; `supabaseAdmin` is used **only** to read `user_id, username` from `profiles`. Never the default anon `supabase` export.
- Profile embeds may come back null — never embed `profiles` in list queries; fill names via the admin lookup.
- The wishlist owner never receives claim state: no `taken`, no `claimedByMe`, no claimer id/name in any response to them. Guests get `taken` and `claimedByMe` only — never `claimed_by`.
- Item titles: trimmed, 1–200 chars. Bulk add: max **100** titles per request. Links: `http://` or `https://` only.
- Shopping paste splits on newlines **and** commas; wishlist paste splits on newlines only.
- UI: CSS variables for colours/surfaces, `<Icon>`, primitives from `components/ui/`. No new dependencies.
- Copy: tab labels `Tasks` / `Shopping`; "Where" options `Just me` + group titles; list byline `by <username>`; done section `Done (n)`; button `Clear done`; wishlist header `<username>'s wishlist`; claim buttons `I'll get this` / `Taken` / `You're getting this — undo`; empty-event button `Add a wishlist`.
- Migration is applied to production **by the controller in the main session with the owner present** — no subagent applies SQL to the live project.

## Review Focus

1. Pasting a real list with blank lines, bullets or numbering (`- milk`, `• eggs`, `1. bread`, `* jam`) must give clean names (`milk`, `eggs`, `bread`, `jam`) — pinned in Task 2.
2. Two quick taps on the same item: the client sends the explicit target `isDone`, never "toggle", so the server ends in the state last shown — pinned in Task 3 (route rejects a non-boolean `isDone`).
3. A guest claims an item someone else claimed since their last refresh → `409` with `error: 'taken'`, and the UI flips it to `Taken` — pinned in Task 4 and Task 6.
4. The owner's wishlist response leaks claim state via an extra field or an extra claims query — pinned in Task 4 (no `list_item_claims` request logged for the owner; no `taken`/`claimedByMe` keys).
5. A personal list (`Just me`) shows up for someone sharing a group with its creator — pinned in Task 1 (SQL test).

**Interfaces:**
- Produces tables:
  - `lists(list_id bigint identity pk, kind text not null check in ('shopping','wishlist'), title text not null check char_length(btrim(title)) between 1 and 200, created_by uuid not null default auth.uid() references profiles(user_id), groups_id bigint null references groups on delete cascade, event_id bigint null references events on delete cascade, created_at timestamptz not null default now())`, with checks `kind='shopping' ⇒ event_id is null` and `kind='wishlist' ⇒ event_id is not null and groups_id is null`, and `create unique index lists_one_wishlist_per_event on lists(event_id) where kind = 'wishlist'`.
  - `list_items(item_id bigint identity pk, list_id bigint not null references lists on delete cascade, title text not null check 1–200 trimmed, link text null check (link ~* '^https?://'), note text null, is_done boolean not null default false, created_by uuid not null default auth.uid(), created_at timestamptz not null default now())`, index on `list_id`.
  - `list_item_claims(item_id bigint pk references list_items on delete cascade, claimed_by uuid not null default auth.uid(), created_at timestamptz not null default now())`.
- Produces SQL functions (all `language sql stable security definer set search_path = public`, execute revoked from `public, anon`, granted to `authenticated`):
  - `list_visible(k text, gid bigint, eid bigint, owner uuid) returns boolean` — shopping: `gid is null and owner = auth.uid()` or `gid is not null and is_group_member(gid)`; wishlist: `can_access_event(eid)`.
  - `can_see_list(lid bigint) returns boolean` — `list_visible(...)` of that row.
  - `can_edit_list_items(lid bigint) returns boolean` — `can_see_list(lid)` and (`kind = 'shopping'` or `created_by = auth.uid()`).
  - `can_claim_item(iid bigint) returns boolean` — item's list is a wishlist, `can_see_list`, and `lists.created_by <> auth.uid()`.
- Policies:
  - `lists`: select `list_visible(kind, groups_id, event_id, created_by)`; insert check `created_by = auth.uid() and list_visible(...)`; update/delete using `list_visible(...) and (created_by = auth.uid() or (groups_id is not null and is_group_admin(groups_id)))`.
  - `list_items`: select `can_see_list(list_id)`; insert check `can_edit_list_items(list_id) and created_by = auth.uid()`; update/delete `can_edit_list_items(list_id)`.
  - `list_item_claims`: select `can_claim_item(item_id)`; insert check `can_claim_item(item_id) and claimed_by = auth.uid()`; delete `claimed_by = auth.uid() and can_claim_item(item_id)`. No update.
- Triggers (pattern of `events_created_by_immutable`, fire only when `current_user = 'authenticated'`): `lists_immutable` (created_by, kind, event_id, groups_id) and `list_items_immutable` (list_id, created_by).
- Grants: `revoke all on lists, list_items, list_item_claims from anon`; `grant select, insert, update, delete on lists, list_items to authenticated`; `grant select, insert, delete on list_item_claims to authenticated`. RLS enabled on all three.

**Interfaces:**

- Produces (types): `ListItem { itemId: string; title: string; link: string | null; note: string | null; isDone: boolean; createdAt: string }`, `ShoppingList { listId: string; title: string; groupId: string | null; groupTitle: string | null; createdBy: string; createdByName: string | null; items: ListItem[] }`, `WishItem extends ListItem { taken?: boolean; claimedByMe?: boolean }`, `Wishlist { listId: string; title: string; ownerId: string; ownerName: string | null; isOwner: boolean; items: WishItem[] }`. **Interfaces:**
- Consumes: `cleanTitles`, `isHttpLink` (Task 2).
- Produces endpoints (declare `/lists/items/...` routes **before** `/lists/:listId...` routes):
  - `GET /api/lists` → `{ success, lists: ShoppingList[] }` — the user's visible `kind='shopping'` lists (RLS decides), newest first, items ordered `created_at` asc; `groupTitle` from `groups`; `createdByName` via admin lookup.
  - `POST /api/lists` body `{ title, groupId: string | null }` → `201 { success, list: ShoppingList }` (items `[]`).
  - `PATCH /api/lists/:listId` body `{ title }` → `{ success }`; `404` when 0 rows updated.
  - `DELETE /api/lists/:listId` → `{ success }`; `404` when 0 rows.
  - `POST /api/lists/:listId/items` body `{ titles: string[] }` → `201 { success, items: ListItem[] }`.
  - `PATCH /api/lists/items/:itemId` body any of `{ isDone: boolean, title: string, link: string | null, note: string | null }` → `{ success, item: ListItem }`; `404` when 0 rows.
  - `DELETE /api/lists/items/:itemId` → `{ success }`.
  - `DELETE /api/lists/:listId/items/done` → `{ success, removed: number }`.
  - Error mapping for every route: validation → `400 { success:false, error }`; Postgres `42501` or RLS-empty insert → `403`; other Supabase errors → `500 { error: message }`.
  - Export `fillUsernames(ids: string[]): Promise<Map<string, string | null>>` (module-internal is fine; Task 4 reuses it).
